# A secret is held only where the act it authorises is performed, and the store two containers share holds none

- **Status:** Accepted
- **Date:** 2026-08-15
- **Ticket:** [#124 Packaging, default configuration, and which container receives which secret](https://github.com/winniel123/verge-asm/issues/124)
- **Map:** [#1 Map: verge-asm v1 spec](https://github.com/winniel123/verge-asm/issues/1)
- **Discharges:** [ADR-0001](./0001-stack-and-runtime.md)'s consequence — *"first-run configuration must now cover which container receives which secret — the split that gives the topology decision its teeth"* — and its sketch of that split
- **Extended by (this rule is *kept*, not withdrawn):** [ADR-0124](./0124-a-backup-carries-data-and-no-secret-and-updating-is-guided-not-self-applied.md) (2026-08-26) builds the shipped, UI-taken backup on the #121 consequence below — *a backup carries the estate and no credential* — making it the export's own invariant. The session and prober keys stay out of every backup and regenerate on restore

## Context

[ADR-0001](./0001-stack-and-runtime.md) chose **one image, two compose services**, and the whole of
its argument for the second service is a blast-radius argument:

> The web tier is what an attacker reaches first: it is the only listener, it parses session cookies
> and TOTP codes, and it renders operator-supplied seed data. Were web and worker one process, a
> foothold in an HTTP handler would also be a foothold on the SSH key to the external vantage and on
> the operator-supplied zone file the map calls "the product's spine."

It then sketched the split:

> - `web` — session key, database credentials
> - `worker` — database credentials, SSH key ([#14](https://github.com/winniel123/verge-asm/issues/14)), operator-supplied zone file

**The sketch does not survive its own argument.** Both services hold the database credential — that
is the first line of both rows — so anything reachable *through the database* is reachable from
`web` by construction. Two of the three items in the `worker` row are in that class or would be put
there by the obvious implementation:

- The **zone file** is evidence. It is parsed into `dns-record` observations that `web` renders on
  `Coverage`, on `Subjects` and in two signals' census
  ([#48](https://github.com/winniel123/verge-asm/issues/48)). Its content is in the database
  whatever the delivery mechanism is. Listing it as a `worker`-only secret protects nothing.
- The **SSH key** is separable — but only if it never enters the database. Nothing said so, and the
  natural implementation of *the operator pastes a key* puts it there, because that is where every
  other operator-supplied value goes.

So the topology decision's teeth were a delivery table, and a delivery table is not a boundary. The
map's note is what makes this worth an ADR rather than a compose comment: **the instance is a
high-value target — its database is a complete, current map of the operator's attack surface.** The
question is not which environment variable each container reads. It is which container can *reach*
each secret at all.

## Decision

**A secret is held only where the act it authorises is performed. Two containers sharing a store
share everything in it, so the store is not the boundary: ~~the database holds no secret at all~~, and
each service's secrets live in a volume only that service mounts. A secret that must be separable is
therefore one its holder generates and never receives — there is no delivery to get wrong.**

> **Reversed for one corpus, at the site that states it**
> ([ADR-0058](./0058-a-superseded-mechanism-is-withdrawn-at-the-site-that-specifies-it.md)).
> [ADR-0126](./0126-verbatim-job-output-is-a-fourth-operational-corpus-retired-by-a-duration-dial-that-ships-bounded.md)
> makes the `Transcript` corpus (verbatim raw job output) the **one** secret-bearing data Postgres
> holds — stored **encrypted** (AEAD, per-value nonce). The rule above is otherwise **kept**: the
> sealing key lives on a service volume and **never enters Postgres**, so a read-only database leak
> discloses ciphertext and no key. Every other secret still lives only where its act is performed.

The test, and it is the one to apply to every secret this project acquires later:

> **If a container that never performs the act can read the secret, the split has not been made.**

| Concern | Decision |
| --- | --- |
| The rule | A secret is held **only where the act it authorises is performed** |
| The shared store | ~~**Postgres holds no secret.**~~ Not the session key, not the SSH private key, not any credential a later channel acquires. **Narrowed by [ADR-0126](./0126-verbatim-job-output-is-a-fourth-operational-corpus-retired-by-a-duration-dial-that-ships-bounded.md): the `Transcript` corpus is held in Postgres *encrypted* under a volume key that never enters it. No other secret, and no key, is in Postgres.** |
| What makes a secret separable | It is **generated by its holder**, into a volume only that holder mounts, and only its **public half or its set/unset state** ever leaves |
| The database credential | The **one deliberate exception**, held by `web` and `worker` alike — and it is not a counter-example, it is the statement of where the real blast radius is. Required, never defaulted: compose reads `${POSTGRES_PASSWORD:?}` and **fails to start** rather than shipping a value |
| The session signing key | **`web`, self-generated** on first boot into a `web`-only volume. Never in the database, because a **read-only** leak of the database — a backup, a replica, an export — would otherwise yield live admin sessions, which [#11](https://github.com/winniel123/verge-asm/issues/11)'s Argon2id hashes deliberately do not |
| The prober's SSH private key | **`worker`, self-generated** into a `worker`-only volume. The operator installs the **public** half on the prober. **No private key is ever supplied to the instance** |
| The zone file | **Not a secret.** It is operator-supplied evidence, uploaded through `web`, stored in the database and read by `worker`. ADR-0001's `worker: … + zone file` is **withdrawn at this clause** |
| The setup token | [#11](https://github.com/winniel123/verge-asm/issues/11)'s, unchanged — generated, written to stdout, single-use, dies with the first admin |
| A secret the operator **types** | Written by its holder, never read back to `web`. `web` renders **set** or **not set** and never a value. Binding on [#119](https://github.com/winniel123/verge-asm/issues/119) |
| What this does **not** claim | That `web` being compromised is survivable. It is not — the inventory is the prize. What is bought is that a foothold in an HTTP handler does not additionally yield **a credential to a machine outside the estate** |

## Rationale

### The database is the prize, so it cannot also be the keyring

ADR-0001's blast-radius argument is right and its sketch under-delivers it, for a reason that is
structural rather than an oversight: **every other design pressure in this project pushes operator
input into Postgres.** [#11](https://github.com/winniel123/verge-asm/issues/11) requires an audit
trail — *who changed the seed list, who launched a scan against production* — which needs an author
and a timestamp, which needs a row. `--scale worker=N` ([ADR-0005](./0005-scan-execution-model.md))
requires every worker to see the same configuration, which needs a shared store. So the default
gravity of the design puts everything in one place, and a security decision that consists of *and
this one thing goes somewhere else* loses to gravity unless it says **why** and **which**.

The why is asymmetric loss. An attacker holding the database holds the inventory — which is the
worst outcome this product has, and #14 already priced the SSH key against it: *"compromising the
instance also yields a VPS — the smaller prize relative to the inventory database."* That pricing is
correct and it is an argument for **not** spending much on the split. It is not an argument for
spending nothing. What separability buys here is narrow and real: the SSH key is the only credential
in v1 that authorises an act **outside the estate**, on a machine the operator provisioned for us
and will otherwise forget about — which is the dangling-asset class this product exists to detect,
with our own name on it (#14's own words).

And the session key's case is different in kind and stronger. Database compromise is not one event.
It has a **read-only** form that is far commoner than the write form — a backup on a NAS, a `pg_dump`
in a home directory, a replica, an export. Password hashes are built to survive exactly that. A
session signing key is not: it converts a read-only historical leak into live admin access with no
password and no TOTP. Putting it in the database silently removes the property #11 chose Argon2id
for.

### Generation beats delivery, and it is why *paste your SSH key* is refused

The runner-up for the prober credential is the obvious one: **the operator generates a keypair and
pastes the private half into the instance.** It loses four times, and only the first is about where
the bytes end up.

- **It teaches the wrong act.** A tool whose subject is the operator's exposure should never ask
  them to paste a private key into a web form. Whatever we do with it afterwards, the key now exists
  in a shell history, a clipboard, a browser autofill store and a password manager, and it existed
  in all of those before we saw it.
- **It has a delivery path, so it has a delivery bug.** A key that arrives over HTTP arrives at
  `web`, and the only route from `web` to `worker` is the database. Every mechanism that keeps it out
  of the database — a socket, a file `web` writes and `worker` reads, an envelope encryption scheme
  with a key-encryption key only `worker` holds — is a second delivery channel built solely to carry
  one secret. A key the holder generates has **no** delivery path and therefore no channel to get
  wrong.
- **Envelope encryption was the near-miss and it loses on the same ground.** Sealing the key in the
  database under a KEK only `worker` holds is a real boundary and it costs a KEK the operator must
  supply and store — which is a new operator-held secret invented to protect an old one, and if it
  is auto-generated it has to live in a `worker`-only volume, which is where the SSH key could have
  gone in the first place. **The volume is the KEK's own storage requirement, one indirection down.**
- **It makes rotation an operator errand.** Under generation, rotation is *generate a new pair,
  render the new public half, the old one stops working when the operator removes it* — an act with
  no secret in flight.

The cost is stated and it is not nothing: **`docker compose down -v` destroys the prober credential
and the session key**, and a database backup restored onto a fresh volume comes up with sessions
invalidated and the prober unreachable until a new public key is installed. Both are recoverable by
an act the operator has already performed once, both fail **loudly** — every session logs out. The
vantage goes `unavailable`, opens a `Gap` and makes `Exposure` non-constructible
([ADR-0005](./0005-scan-execution-model.md)) — and neither can fail **silently**, which is the
property this repository consistently buys at higher prices than this.

### The one shared secret is the statement of where the boundary really is

`web` and `worker` both hold the database credential and there is no version of this design in which
they do not: `web` renders the estate and `worker` writes it. Rather than dress that up, it is the
Decision's own row, because it is what makes the rule readable. **The split is not between two
containers. It is between the store they share and the two stores they do not.** A future session
reading *the secrets are split by blast radius* and reaching for a third `worker`-only credential in
the database will be reaching past this row.

The `${POSTGRES_PASSWORD:?}` requirement is #11's *no default password ships* applied one layer
down, and it is deliberate friction of exactly the kind #11 already accepted when it made the
operator read `docker compose logs` for a setup token. It does not violate the map's *no external
services to provision*: Postgres is in the compose file, and setting one variable is not
provisioning a service.

### What this rule does to the surfaces that do not exist yet

The rule is written to bind forward, because the secret population is going to grow and the growth
is already ticketed. [#119](https://github.com/winniel123/verge-asm/issues/119) will decide
notification channels, and every candidate — SMTP credentials, a webhook URL with a token in it, a
chat integration secret — is a secret the operator **types** and a worker **uses**. Under this rule:

- it is written to `worker`'s store by `worker`, never persisted by `web`
- `web` renders **set** / **not set** and a test-send result, never a value, never a masked value
  that can be un-masked by reading the database
- it is out of every backup that carries the estate, which is a property #121's retention ruling
  should be told about rather than discover.

The prohibition that falls out and is worth stating separately: **there is no "show" affordance on a
secret anywhere in this product.** A value the operator can read back from the UI is a value `web`
can read, and the rule is exactly that `web` cannot.

### Where this is thin, stated rather than smoothed

- **No threat model has been written, and this reasons from one implicitly.** The assumed adversary
  reaches `web` through an HTTP handler or reaches a database backup at rest. An adversary with
  arbitrary code execution on the host reads every volume and the split buys nothing. That is stated
  rather than defended, and it is the same posture ADR-0001 took.
- **The asymmetric-loss argument is a judgement, not a measurement.** *A VPS is a smaller prize than
  the inventory* is #14's sentence and this ADR leans on it. Nobody has enumerated what an attacker
  does with a prober. The one concrete thing they do is **fabricate observations**, which #14 already
  says no transport prevents — so the marginal loss from the key specifically is genuinely small, and
  the strongest limb of this ADR is the **session key**, not the SSH key.
- **Two volumes is one more moving part than one.** An operator who mounts neither gets a fresh
  session key on every restart (everyone logs out on every `up`) and a fresh prober keypair (the
  vantage never verifies). That failure is loud, and the shipped compose file declares both volumes,
  so it is reachable only by editing the file — but it is reachable, and nothing in the model
  detects *your session key is ephemeral*.

## Consequences

- **New rule, one sentence:** a secret is held only where the act it authorises is performed, and the
  store two containers share holds none.
- **[ADR-0001](./0001-stack-and-runtime.md)'s secrets sketch is withdrawn at the site that specifies
  it** ([ADR-0058](./0058-a-superseded-mechanism-is-withdrawn-at-the-site-that-specifies-it.md)).
  Read alone and in the present tense, *`worker` — database credentials, SSH key, operator-supplied
  zone file* would have a session build a delivery table and call it a boundary. Its topology
  decision, its blast-radius rationale and its `web`/`worker` split are **untouched and confirmed**.
  What is withdrawn is the row.
- **The compose file gains two named volumes** — `web-state` and `worker-state` — beside `pgdata`,
  and the shipped file is the artefact that carries this ADR. The full shape is in
  [`packaging-and-configuration.md`](../spec/packaging-and-configuration.md).
- **No private key is ever an input to the deployment.** The prober keypair and the session key are
  both generated in place, which removes two rows from every first-run document that would otherwise
  have to explain how to produce them safely.
- **`web` renders no secret value, ever.** This is a UI constraint as much as a storage one, and it
  reaches [#123](https://github.com/winniel123/verge-asm/issues/123)'s `Seeds` screen (the prober's
  **public** key is rendered. Nothing else is) and [#127](https://github.com/winniel123/verge-asm/issues/127)'s
  audit trail (a secret being **set** is an auditable act. Its value is not an auditable datum).
- **[#119](https://github.com/winniel123/verge-asm/issues/119) inherits a constraint rather than a
  design.** Whatever channels it picks, their credentials are `worker`'s, written by `worker`, and
  invisible to `web` and to the database.
- **[#121](https://github.com/winniel123/verge-asm/issues/121) inherits a fact.** A database backup
  carries the whole estate and **no credential**, which is a better property to have decided than to
  discover, and it is the reason a backup does not need to be treated as a keyring.
  > **Relied on and extended, 2026-08-26 by [#664](https://github.com/winniel123/verge-asm/issues/664) /
  > [ADR-0124](./0124-a-backup-carries-data-and-no-secret-and-updating-is-guided-not-self-applied.md).**
  > The v3.18.0 UI backup is built on exactly this fact: it is a Go-native logical dump of estate +
  > config only, and *data-only, no secret* is made the export's own invariant (the session key and
  > prober key are never read by the backup path and regenerate on restore). This rule is **kept in
  > full** — ADR-0124 withdraws nothing here.
  >
  > **BOUNDED at this site, 2026-09-05, by
  > [ADR-0160](./0160-a-backup-redacts-a-reversible-cleartext-credential-and-carries-a-hash-or-an-externally-keyed-ciphertext-and-restore-re-applies-the-same-redaction.md)
  > ([ADR-0058](./0058-a-superseded-mechanism-is-withdrawn-at-the-site-that-specifies-it.md)).**
  > *Credential* here means a secret held to **perform an act**, which is this ADR's own subject. It
  > does not mean the archive carries no credential **material**. `account.password_hash`,
  > `personal_token.token_hash` and the `account.totp_secret` ciphertext all ride with their rows,
  > because a restore must reconstitute login and tokens. None of the three is reversible from the
  > file, and a weak password is still guessable offline from its hash. So *"does not need to be
  > treated as a keyring"* holds in this ADR's sense and must not be read as *needs no care*:
  > **treat a backup file with the same care you treat access to `pgdata`**
  > ([`backup-and-restore.md`](../guides/backup-and-restore.md)). ADR-0160 also redacts the two
  > **cleartext** columns the database does hold, which narrows what the archive carries rather than
  > widening it.
- **Cost: zero.** Nothing has shipped, no compose file exists, no key has been generated.

## Alternatives rejected

| Alternative | Why not |
| --- | --- |
| **ADR-0001's sketch as written** — a delivery table: `web` gets these environment variables, `worker` gets those | It is not a boundary. Both rows begin with the database credential, so anything routed through the database is reachable from `web` whatever the table says — and the zone file **is** routed through the database by every other requirement in the project, while the SSH key would be by the obvious implementation of *paste your key*. The sketch's own argument (*a foothold in an HTTP handler should not be a foothold on the SSH key*) is the thing it fails to deliver |
| **The operator pastes the prober's private key** — the *runner-up* | It teaches a self-hosted security tool's operator to paste a private key into a web form; it creates a delivery path from `web` to `worker` whose only honest route is the database; and every mechanism that avoids the database is a second channel built to carry one secret. Generation has no delivery path at all |
| **Seal the SSH key in the database under a `worker`-only key-encryption key** — the *near-miss* | A real boundary, and it needs somewhere to keep the KEK. Auto-generated, that somewhere is a `worker`-only volume — which is where the key could have gone with no crypto. Operator-supplied, it is a new operator-held secret invented to protect an old one, and it fails `docker compose up` for the same reason a pasted key does |
| **One service, and rely on process isolation inside it** | ADR-0001's topology decision, unreopened. This ADR is about what the second service is *for*; removing it removes the question rather than answering it |
| **Docker/compose `secrets:` for everything, including the generated keys** | Right for the one secret the operator supplies (the database credential) and wrong for the two they do not: a compose secret is a **delivery** mechanism, and the whole finding is that a secret with no delivery is the separable kind. The shipped file may use `secrets:` for `POSTGRES_PASSWORD`; it has nothing to deliver for the other two |
| **Keep the zone file out of the database — a `worker`-only mount, as ADR-0001 had it** | It is evidence, not a credential. Two signals read it, `web` renders their census and their `not-evaluable` reasons, and [#48](https://github.com/winniel123/verge-asm/issues/48) requires the batch that reads it to record the **zone**, which is a stored fact. Keeping the bytes out of the store while the parse is in it protects nothing and costs the supply instant the currency bound needs |
| **Encrypt the whole database at rest with an application-held key** | It answers a different threat (media theft) at the price of making every backup unreadable without a key the operator must keep somewhere this ADR would then have to rule on. Filesystem or volume encryption is the operator's, and it is one line of deployment guidance rather than a modelling decision |
| **A "show secret" affordance for support** | The rule is that `web` cannot read them, so the affordance cannot exist. Where an operator needs to know a value they no longer have, the answer is to set a new one — which is what generation makes cheap |
